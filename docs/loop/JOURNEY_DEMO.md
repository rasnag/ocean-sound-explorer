# Try Curiosity Engine locally

This launcher is a local composition facade, not a public release. Use invented information only. It does not approve content, select real offer/privacy terms or complete a parent task card.

## Start and follow one request

The root operator supplies the final integrated start command and two actual local links after checks. Open the parent origin `/` for the obvious start page. The facade module itself is an importable API, not a command that silently starts services.

1. Choose **Start as the parent** and use an invented `@example.invalid` address. In the local runner console type `inbox`; enter the simulated verification token in the parent page.
2. Review TEST permissions, set up an invented child and use the explicit test-trial control. A fresh store has no pre-created family, consent, child or active trial.
3. Type **What changes make this pretend platform tip?** Save it, then explicitly submit the same wonder for production. Record the original receipt; saving alone books nothing.
4. Type `operator` in the local runner console for the invented founder credentials and current six-digit code. Sign in on the founder origin and accept the same request in the queue.
5. Use the mock generation workbench, then record TEST review results and release a TEST snapshot. The provider is a fixed deterministic toy, not real AI or a scientifically validated answer. An unrelated question is a mismatch, not silently answered or rewritten.
6. Use the integrated readiness control and return to the family page for that same assignment. Start a play, predict, configure, test, wait for the acknowledged save, reload and resume that exact play. Inspect its activity record.

These are the target steps, not a claim that every step currently works. The landing lists all thirteen **demo capabilities**, reported by the integrator rather than observed completion. WORKING means implemented code capability; SIMULATED means a fixture substitute; MISSING means absent/unverified. Even working code uses simulated verification, permission, offer, provider and TEST-checklist methods. No credentials, TOTP seeds, mock codes or email addresses are served on the landing page.

## Current boundary

Explicit trial activation and the parent-origin play/save/reload/resume/activity seam remain the integrator's separate work. Until its exact source is checked, reviewed and observed, these capabilities must stay MISSING. Never use a separate seeded saved-player fixture as proof of the same journey. The root's runner owns console `operator`/`inbox` commands. Generate the current code locally using the operator TOTP secret; never print or place the seed in HTTP, reports or telemetry. Closing the demo preserves the owned persistent directory so a later start can resume actual invented user actions. No reset is performed.

## Developer contract

`startJourneyDemo({env,directory,createProtectedJourney,createAssets?,parentPort?,founderPort?,timeoutMs?})` returns `{parentOrigin,founderOrigin,close,getDemoState}`. The first three expose no credential data. The validated async `getDemoState` is a trusted console-only channel. Default request/state deadline is 10 seconds; a validated 1–10000 ms override supports deterministic lightweight tests.

The injected integrator factory receives `{env,directory,serve}` and returns two distinct unlistened protected HTTP servers, core `close()` and async `getDemoState()`. It owns empty fresh-store schema/operator/invented offer/capacity bootstrap, actual protected trial/Start/action/activity/readiness and all persistent key/store semantics. No families or workflow records may be seeded. Persistent reopen keeps prior actual invented actions. The facade listens only on `127.0.0.1`, closes HTTP before core and assets, attempts every cleanup and preserves data.

The optional assets factory returns `{serve(req,res,next),close}`. Configure Vite with the same application root containing `index.html`, `mode:'development'`, `appType:'spa'`, preview flag `1`, `server.middlewareMode:true`, `hmr:false`, **`ws:false`**, `fs.strict:true`, and `fs.allow:[applicationRoot]`. Vite 8 can still open a wildcard WebSocket listener when only `hmr:false` is set; `ws:false` is essential. Root must verify exactly two listeners, both loopback, and none on 24678 or a wildcard.

The persistent directory must resolve outside the entire Vite source root, including symlink/junction resolution. Do not put keys or state under application assets. Linking `node_modules` outside the allowed root can cause Vite `/@fs/` imports; the facade refuses those paths, so use dependencies installed inside the actual served root rather than weakening the allowlist. Actual preview routes must render the intended screens, not About.

Parent `serve` runs only after the protected handler authorizes its route/Host/Origin. Exact GET `/` renders the home; `/?v=...` is not home. Existing parent HEAD/POST `/` return upstream 404; the facade's defensive 405 applies only if directly called. Vite's own SPA misses and listener count require integrated observation; fake-middleware unit tests prove only callback behavior. Error/timeout responses are generic. The facade does not proxy, rewrite identity headers, mint cookies or implement a third play server.

Cookies are host-scoped, not port-isolated. Founder `loop_session` with Path `/` reaches the parent server and is ignored there; adult `loop_adult_session` uses Path `/adult`. Real core checks must prove wrong-role cookies and opposite-port Origins grant nothing. The landing's status labels and NodeHTTP fake-factory tests cannot prove actual integrated authorization.
