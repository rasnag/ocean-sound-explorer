# CODEX-07-A synthetic play service contract

Draft v1.1, 2026-11-11. Application implementation for review; not an accepted card or production service.

Authority: engineering architecture v1.2, APPROVAL-004, SHA-256 `02adc2e0bf0910092f0888a126cdebe98adc35a177679bf124e0e79393532b79`; CODEX-00-B contracts 1.1.1, wire 1.1.0; authorized CODEX-07-A approved-copy blob `c40becc33e8f92a2418adf7e662c24b42ea79fd1`. Applicable interfaces are WM-06 deterministic transitions and WM-07 StartPlay/CommitAction/ResumePlay. ADR-E01/E02/E05, the common household-first lock hierarchy, atomic play consistency and v1.2 recovery invariants govern. No independent module architecture is introduced.

The synchronous `createSyntheticPlayService({db,env,catalog,journal,clock=Date.now})` returns async `start`, `commit`, `resume`, `reconcile` and synchronous `health`. Configuration passes existing resolveLoopConfig with exact local-synthetic mode. The journal must be a branded actual filesystem-factory instance. Real PGlite transaction/query support is required. SQL service modules remain outside client imports.

Scope is exactly `{household_id,child_id,assignment_id,play_id,revision_id,consent_epoch}`. IDs are lowercase UUID strings; epoch is a positive safe integer. HTTP authority comes from an immutable copied developer capability map. This fixture is not verified adult/parent identity; founder login grants no play authority. Every operation, including duplicates, rechecks current latest active consent and child/request/revision/publication/assignment relationships.

Catalogue entries are exactly `{household_id,revision_id,spec,starting_path,starting_reason}`, copied and recursively frozen. Complete validation and transitions use existing validateAdventure/createPlayer or validateAssistedAdventure/createAssistedPlayer. Published relational rows remain synthetic scaffolding, not human content approval. Metadata pins canonical full-spec SHA256, versions, scope, original epoch and human-selected synthetic path/reason. Changed catalogue bindings reject.

Start input is exactly `{contract_version:'1.1.0',command_id,play_id,consent_epoch,revision_id,pattern_version:'fixture-1',engine_version}`. It creates action0/event0, actual initial engine snapshot and events[]. Existing seed/uninitialized plays cannot be adopted or reset. Exact Start retry preserves its receipt. Resume input is exactly `{play_id,revision_id,consent_epoch}`. Commit accepts the exact play_action 1.1.0 envelope and finite actions of its actual engine. Client outcome, clock, specification, scope and extra fields confer no authority and reject without effects.

Each operation owns a real outer transaction. Lock order is household/latest consent → request → revision → assignment → play; unused common hierarchy levels are skipped. The process-local queue serializes PGlite operations across factory instances, while actual SQL locks establish withdrawal ordering. Multi-host support is unproven. Write-first may commit a fact preceding withdrawal; confirmation after withdrawal cannot disclose a private checkpoint. Replay uses immutable original envelopes with their original epoch. Current callers must independently pass both latest active and original pinned epoch; epoch continuation remains lifecycle integration.

Action dedupe precedes sequence CAS. Changed successful key conflicts. Exact duplicate returns its original result even after newer actions, including while a newer action awaits journal confirmation, provided its own journal record and current authorization/history verify. This is historical receipt retrieval, not Resume or a new save: it returns only that command's old receipt, adds no rows, exposes no newer candidate and does not clear journal outage health. Resume still fails closed on a current pending command. New actions remain blocked on that play until confirmation; service-wide actual journal outage additionally closes new writes.

Configure alone creates no trial. Test requires exact current committed Predict/Configure references and derives finite outcome through the actual engine. Compare requires two actual committed trials in the same play. Engine1 supports comparison but not assistance; it does not gain invented help behavior. All gameplay inserts/updates use tx.query.

Each action writes one existing play_events row with exact typed batch `{events:[...]}`, preserving original unique action/sequence constraints. Action and event cursors are independent: Predict/Configure/Test produce action3/event4. Events carry contract, kind, deterministic action/index event ID, play/action IDs, server cursors, revision/pattern, server_observation source and UTC whole-second server_at (`YYYY-MM-DDTHH:MM:SSZ`). Server order is sequence-based.

Checkpoint is exactly `{checkpoint_id,last_action_sequence,last_event_sequence,state}`, with state deep-equal to the actual engine snapshot, including pins, references and tries.

The primary transaction atomically stores command, lowercase 64-hex canonical digest, candidate result, event batch, checkpoint, authoritative play sequence and pending journal intent. Its predetermined acknowledged result is a candidate, not an exposed acknowledgement. SQL ack_state pending means PENDING DURABILITY. Candidate Test batches contain test_resolved/progress_saved so the entire candidate commits atomically. No pending response exposes checkpoint/events or an older checkpoint. Future projections MUST join the owning command's acknowledged marker before presenting progress_saved as fact.

After primary commit, with no SQL transaction held, append writes canonical UTF8 length/checksum-framed synthetic records to play-journal.log, calls actual FileHandle.sync and verifies the stored record. Service verifies returned reference and body, then reauthorizes under SQL locks to set only the acknowledgement marker. No second gameplay effect occurs. Record is exactly `{version:1,synthetic_only:true,record_id,household_id,play_id,primary_commit_id,command_digest,result}` and durability_ref is `local-fsync:<record_id>`.

Acknowledged results are exactly `{status:'acknowledged',mode:'local-synthetic',acknowledgement_scope:'single-host-process-recovery-only',production_ready:false,play_id,action_id,primary_commit_id,durability_ref,checkpoint,events}`; Start action_id is null. All exposed data is defensively copied. Primary commit followed by journal/confirmation failure returns retryable_unacknowledged with stable play/action/primary IDs, no checkpoint/events. Same-key retry or trusted reconcile backfills original intent/marker without extra trial/event. Resume never silently backfills: latest pending returns pending/503 without data. Missing/corrupt acknowledged journal evidence returns recovery_required, never older state.

health() synchronously returns `{state:'healthy'|'journal_unavailable'}` for journal availability. Actual append/read failure sets journal_unavailable; successful backfill restores healthy. A withdrawn play's pending marker alone does not create journal outage or block unrelated plays. Reconcile has no HTTP/admin endpoint.

Resume reconstructs original commands from sequence0 and validates full digests/results, typed event batches, checkpoint and all cursors/session sequence. A completely unstarted play, with no session, metadata, start, checkpoint, action or event rows, returns denied without writing or quarantine; a later valid Start remains possible. Partial stored history, legacy placeholder seeds and inconsistent successfully read records fail closed. SQL reads are outside the pure consistency-validation catch: transient SQL failures map to generic recovery_required without permanent quarantine. Only detected inconsistency in present stored history can quarantine that play for the process lifetime. No service code disables triggers or resets history.

Journal directories must preexist, be developer-owned and exclusively synthetic. Adapter rejects redirection, symlinks, nonregular/hardlinked log files and opened-path replacement. Unix ownership/mode checks apply where available; Windows ACL administration remains developer responsibility. Concurrent opens are unsupported; same-process duplicate opens reject. Reopen after close/killed writer verifies all frames; truncation/checksum corruption throws recovery_required and preserves bytes. Partial writes poison the adapter. No acknowledged tail is silently discarded. Optional exact trusted `testHooks:{beforeAppend:async(record)=>void}` supplies a defensive clone before a new append; return is ignored. It cannot replace append, sync, read or confirmation and is never HTTP input.

HTTP is an actual node:http server requiring explicit127.0.0.1 binding. Only POST /play/start, /play/action, /play/resume exist. Bearer header capabilities only; no mint/admin/SQL endpoint. Actual Host port and absent-or-exact-origin Origin are enforced. Forwarded, identity, cookie, duplicate authorization and query credentials reject. Ordinary User-Agent is permitted and never confers identity. JSON body/header bounds are8KiB, timeouts10seconds. Responses are no-store, nosniff, no-referrer, CSP default-src none, no CORS. Success200; invalid400; credential401/403; scope403; conflict409; pending/recovery503. Generic exceptions expose no credentials/private payload and are not logged.
