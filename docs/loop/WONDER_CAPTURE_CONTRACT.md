## Primary, journal and acknowledgement

Phase one commits immutable request/source/payload and a pending command. Command metadata contains IDs, HMAC, an encrypted recovery envelope and immutable result reference; it has no raw question or parent context. AES-256-GCM uses a domain-separated household encryption key and authenticated record header. The independent record also has a household HMAC. The encrypted snapshot includes the original normalized command, actor/epoch/profile, request/source/predecessor, payload reference and result reference. That is recovery evidence for a controlled isolated reconstruction; no automated full-primary-loss restore is claimed. A journal command absent from primary is quarantined, never treated as permission to mint another identity.

After the actor transaction ends, the genuine branded wonder journal appends the exact encrypted record. It writes every framed byte, fsyncs, reopens, checks the same filesystem identity and verifies exact frame content. Then a fresh withSession rechecks current consent/profile/source/command and persists only the false-to-true acknowledgement marker. No actor transaction contains journal IO and there is no nested withSession.

An acknowledged response has wonder_capture/synthetic_only/TEST-v1 base, state acknowledged, command_id, request_id, source_scope_version, child_id, view_context, acknowledgement_scope single-host-process-recovery-only and production_ready false. There is no production receipt, deadline, received time, reservation or capacity result.

Primary commit followed by pre-append failure returns retryable_unacknowledged with the exact pending reference and writes_closed true. It never means Saved. Same-key save or explicit reconcile backfills the original encrypted record and acknowledges the same source. A new Save requires the selected current profile. After a valid primary fact commits and the profile subsequently changes, the parent must select the current profile and explicitly reconcile that existing command. Reconciliation permits an older stored profile version only for the same actor, household, child and unchanged active consent epoch, preserving the original source/profile/HMAC and creating no new save or profile reattachment. Future-profile, other-actor/child/epoch and stale new writes remain denied. An actual journal failure closes new writes in the process; persisted pending primary commands also close new writes after reopen. Unknown/corrupt/missing acknowledged records, key loss, wrong keys and orphan journal commands quarantine the scope. No key rotation or replacement receipt silently repairs uncertainty.

The journal requires an existing absolute exclusively owned directory. Parent symlinks/junctions, nonregular or hardlinked logs, duplicate same-process directory opens and replacement of opened directory/file identity fail closed. Unix owner/mode checks are enforced where available; Windows ACL ownership is a caller prerequisite. Structural startup checks verify bounded canonical length/checksum frames without truncation. Household HMACs are verified when the household key is supplied for record reads/appends. No key is retained by the adapter after an operation. It uses wonder-journal.log, never accepted play records. Bounds are 64 MiB, 10000 frames and 128 KiB per frame, with at most 1000 household records returned. The exact test hook beforeAppend can fail before a real append; its return value cannot fabricate durability.

These are single-host process-recovery mechanics, not multi-host locking, host/power-loss protection, a separate production failure domain, approved backup restore or completed deletion/key destruction. CODEX-00-F/10-C/10-D/13 retain those obligations.
