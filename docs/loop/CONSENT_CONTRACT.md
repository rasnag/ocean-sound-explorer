# Local synthetic permission enforcement

Implements ADR-E02/E05, RecordConsent/WithdrawConsent and current-policy/epoch authorization in the existing play and entitlement services. DECISION-040/APPROVAL-007 permits invented local families and TEST-v1 permission only. This is not approved legal wording or real parental consent.

`createSyntheticConsentService({env,db,access,clock,policyVersion:'TEST-v1'})` requires the exact local-synthetic environment, actual PGlite, migration007 and trusted adult issuer. No network adapters, new dependencies, UI or production configuration. The adult issuer adds `withSession(token,callback)`: its existing issuer→household→account→session lock order validates the current enabled, unexpired, unrevoked adult and awaits a DB-only callback within the same transaction. Callback failures roll back, domain errors remain internal, actual40001/40P01 can retry at most three times. Callbacks must be retry-safe and never send external effects.

The HTTP constructor accepts an optional trusted `consent` service. GET`/adult/consent`, POST`/adult/consent` and POST`/adult/consent/withdraw` use the existing HttpOnly SameSite=Strict Path=/adult cookie. Founder credentials never grant family scope. The record body has **five** exact named fields: command_id, policy_version, required_service, optional_contact, optional_story. Withdrawal has command_id and policy_version. No identity, timestamp, epoch or arbitrary scope is accepted. The setup handoff's prose saying “six-field” is a count typo; the exact named contract and protected probe both specify these five. No requirement or policy choice changes.

Status exposes only simulated permission state and epoch, never child data or identity. Active TEST-v1 is required; absent, withdrawn or unknown policy deny personalized use. Optional permission defaults false and does not control required service. Affirmation of an already active current policy changes optional flags without changing epoch. Required refusal while active withdraws; other refusals grant nothing and write no child data. Withdrawal invalidates every prior active row, appends a successor withdrawn epoch, clears optional flags and fences both current/old receipts and fresh operations. Reconsent advances again and never updates old play bindings. Historical command receipts remain immutable facts and cannot reactivate permission.

Commands deduplicate under household lock using actor+kind+validated intent digest; changed actor/kind/payload for the same household/key conflicts. Receipt and permission changes commit together. SQL failure rolls both back. Current session authorization always precedes returning a duplicate. No tokens are persisted in receipts. The issuer hashes all opaque session tokens independently.

Affirmative mutations use durable local fixture limits:120 global and30 per household per60000ms window. Exact committed retries do not consume budget. Backward clock fails affirmative mutation with no committed changes; it cannot reset/replenish quota. Required refusal and withdrawal bypass quota so it cannot prevent revocation. These provisional synthetic limits are not production policy or capacity evidence. Existing raw Host, identity/forwarded-header rejection, exact Origin for mutations, strict body/cookie bounds, no-store/no-referrer/nosniff and loopback-only listening remain. Errors expose only generic messages; no request or credential logging.

Existing play Start/Commit/Resume and entitlement activation/transition/allowance reads check latest active TEST-v1 and matching epoch inside the household transaction. Play also rechecks after journal durability before returning private state: withdrawal between primary commit and journal acknowledgement cannot leak the acknowledgement/private response. Already committed play remains a historical fact, not renewed permission. Current developer-only play capabilities remain fixture capabilities, not adult-verification proof.

Migration001–006 have no actual notification/delivery queue, external generation-dispatch ledger or content-access-grant table. Therefore queue suppression, processor cleanup and later module integration are **not implemented or claimed**. Assignment rows are existing fixtures; their personalized access is fenced through the implemented play service. Child creation/setup is02-C and has no public route here. Independent revocation/recovery journal, deletion, key-management, scheduler, provider, real consent/privacy and public admission remain gated. All real data, email sending, provisioning, purchases, extra API generation and deployment remain prohibited.

Verification uses real disposable PostgreSQL/PGlite and actual local HTTP, including verified invented accounts, authenticated founder attacks, household isolation, policy/epoch fences, lifecycle/optional flags, SQL rollback, quota reset/backward clock, cache/response/process-log leak checks and both journal-boundary orders. Tests and independent review must actually pass before technical acceptance.

The sole app regression file also runs these full HTTP/service attack and lifecycle cases without any dependency on the planning checkout. It additionally exercises entitlement `apply`, concurrent distinct commands, refusal during exhausted quota and actual SQLSTATE40001/40P01 retry limits/rollback. The separate controller probe remains independently protected.

State-label precedence: an unknown policy is reported as `policy_mismatch` even if its fixture row is withdrawn. Both states deny access; service-created rows always use TEST-v1. Authorization uses the issuer's timestamp captured for the transaction. The separate consent-clock reading is used only for the fixture mutation quota, never to extend or replace session validity. Defaults both use Date.now; tests inject the same controlled clock. A quota clock moving backward can only deny an affirmative mutation. Permission rows and quotas persist across service instances in the disposable database; memory-mode tests do not establish survival of process loss.
