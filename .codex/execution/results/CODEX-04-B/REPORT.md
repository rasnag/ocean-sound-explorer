## Stage 1 schema interface for stage 2

Migration 011 is additive. It preserves the existing core reservation and composite entitlement-claim schemas. `production_capacity_buckets` stores trusted immutable global configuration with exact columns `bucket_id, policy_version, offer_version, starts_at, ends_at, coverage_end, limit, synthetic_only`. SQL uses quoted `"limit"`; parameterized SELECT/INSERT callers must do likewise. No browser configuration or seed endpoint is introduced.

`production_capacity_bookings` binds `(household_id,request_id,booking_id,bucket_id)` to the real core `(household_id,reservation_id,request_id)` through a composite FK. Receipt booking_id is that reservation_id. Admission must lock the global bucket and count joined core reservation rows with state booked OR completed across households. Released rows free live capacity; completed calendar usage does not. There is no parallel state flag or in-memory counter.

`production_receipts` has the common receipt fields plus household_id. Its immutable claim_id mapping is backed by the real `(household_id,request_id,period_id)` entitlement-claim FK. The insertion guard compares receipt time to the existing request original_received_at. It enforces whole-second receipt instants and due=received+86400 seconds. Old claim/capacity state may legitimately advance without changing receipt identity.

`production_commands` stores immutable original actor/profile/epoch/source provenance, keyed digest, namespace, primary commit/record IDs and encrypted sealed_record. Use distinct server command_id and caller idempotency_key; equality is not required. One request can have only one production command. Changed-payload reuse must conflict before fresh eligibility checks. A different key cannot book the same source again.

`production_acknowledgements` is a separate immutable, FK-bound marker. Presence of original_received_at, claim, capacity mapping, receipt or command alone never proves acknowledgement. Insert the marker only after independent append/fsync/reopen proof and renewed authorization. Family projection must join this proof before exposing Received. SQL cannot establish external fsync or trusted authorization; that belongs to stage 2.

## Stage 1 journal interface for stage 2

`createSyntheticProductionJournal({env,directory,keys,testHooks?})` is async. `keys` is exactly `{keyForHousehold}`; the synchronous callback returns a 32-byte Buffer. No global receipt key is required by this interface. An existing exclusively owned directory is required. The dedicated file is `production-journal.log`. Returned own methods are `seal(fact)`, `fact(sealedRecord)`, `append(sealedRecord)`, `reconcile(sealedRecord)`, `records(household_id)` and `close()`. `namespace_verifier` is an own string property. `isSyntheticProductionJournal` provides module-private branding. Helpers and `productionError`, `keyed` are exported for service use.

Fact exact required fields: `format:'production-committed-fact-v1', household_id, adult_id, command_id, record_id, primary_commit_id, canonical_digest, namespace_verifier, command, receipt`. Optional `binding` is exactly `{profile_version,consent_epoch,wonder_version,scope_version}` and must match the command. Store this original binding; current recovery authorization must not rewrite it. `command` is the exact common00B SubmitProduction command, without household, selection or client deadline additions. `receipt` is the exact common receipt. All top-level identities are lowercase UUIDs. The service must calculate the keyed canonical_digest and bind source, actor, epoch and payload; the journal authenticates storage and structural consistency rather than manufacturing authorization.

Call seal inside primary preparation and persist that exact sealed_record with the actual primary transaction. Only after primary commit call append OUTSIDE the actor transaction. Append/reconcile resolve to `production-fsync:<record_id>` after fsync and reopening/revalidating the physical file. Retry uses the persisted sealed record; resealing with a fresh nonce is not an identical retry. The journal rejects a different sealed record under an existing command identity. `fact` authenticates/decrypts a supplied record but does not assert that it has been physically appended; append/records provide that independent evidence.

Physical records contain opaque IDs, keyed digest, namespace and encrypted command/receipt. Receipt timestamps and optional binding are encrypted. AEAD authenticates each header; chained per-household HMAC frames authenticate order and the namespace manifest. Constructor authenticates and decrypts every frame immediately. Wrong keys, invalid UTF-8, duplicate JSON names, changed framing, partial tails and changed paths quarantine without truncation. Existing empty logs are corrupt. A fresh log gets a random namespace manifest, fsync, and on non-Windows a directory-entry fsync. Windows filesystem/ACL durability remains a caller/platform evidence prerequisite.

`beforeAppend` runs after prior-record reconciliation but before bytes are written, enabling a primary-commit/journal-outage fixture. Its failure returns journal_unavailable and preserves the log. Ambiguous write/fsync/reopen failure quarantines the instance; reopening validates the actual bytes. There is no successful-record memory cache. All serialized operations reopen and verify the file. Close waits for queued work and releases the process-local directory ownership guard. Returned records/facts are independent snapshots; copied key material is zeroed after use.

A deleted/replaced log creates a different namespace or invalidates the open file identity. Stage 2 must compare the primary command namespace to the opened journal, verify all primary acknowledgement references against actual records and quarantine missing recovery coverage. A correctly framed complete-suffix loss cannot be diagnosed from that file alone; primary coverage checks are mandatory. Total loss of both authorities is not solved by this local adapter. No truncate/repair API is provided.
